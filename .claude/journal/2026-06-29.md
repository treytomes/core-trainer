## Learning

### Core Wars concepts
- Core Wars is a programming game where warrior programs battle in shared memory
- Warriors are written in Redcode, an assembly-like language
- The goal is to terminate opponent processes while keeping your own alive

### Key architectural decisions
- Used C# records for immutable `Instruction` type with `with` expressions for modifications
- Implemented process queues (one per warrior) for handling SPL (split) instructions that create new execution threads
- Memory wraps around using modulo arithmetic: `((address % size) + size) % size`
- Round-robin execution: each warrior executes one instruction per cycle

### Redcode execution model
- Instructions execute sequentially unless jump opcodes redirect flow
- DAT instruction kills the executing process (used as "bombs")
- SPL creates a new process at target address, enabling parallel execution
- Addressing modes make warriors more dynamic (indirect allows pointer-following)

### Classic warrior strategies
- **Dwarf**: Uses indirect addressing to bomb locations, increments a pointer to spread bombs
- **Imp**: Minimal one-instruction warrior that creates a trail of copies

### Code review insights
- **Circular distance calculation**: In circular address spaces, must use `min(linear_distance, size - linear_distance)` to find true distance
- **Fork bomb prevention**: ICWS '94 standard specifies 8000 max processes per warrior
- **Validation importance**: Public APIs need parameter validation (bounds, null checks, range checks)
- **Code duplication**: Duplicated switch statements are maintenance hazards; extract to helper methods
- **XML documentation**: Required for all public APIs per coding standards

### Technical Decisions Made

**Why Generic Host?**
- Future-proof: Can easily convert to Worker Service, Web API, or gRPC
- Standardization: Same patterns as ASP.NET Core
- Ecosystem: Access to entire Microsoft.Extensions.* ecosystem

**Why Serilog over ILogger alone?**
- Superior sink ecosystem (50+ sinks available)
- Better performance for structured logging
- More flexible configuration
- Industry standard in .NET community

**Why YAML over JSON?**
- Developer experience: Easier to read and edit
- Comments: YAML supports inline documentation
- Industry alignment: Matches Kubernetes, Docker Compose patterns
- Less syntax noise: No quotes/commas

**Why Singleton lifetime?**
- Services are stateless (except Random in BattleService - could improve)
- Avoids allocation overhead
- Safe for concurrent access (no mutable shared state)
- Matches application lifetime
