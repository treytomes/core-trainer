# Journal Entry - July 17, 2026

## HeadTrack width campaign: does context window scale with model size?

Continuing the [HeadTrack](../../examples/CoreTrainer.Examples.HeadTrack/) probe (built 2026-07-13):
measure **D**, the reliable head-tracking distance (how many one-cell L/R head moves a NoPE transformer
follows over a windowed tape before losing track), and how it scales with model **width** (EmbedDim), all
other axes pinned. This is the primitive the scrollable-tape Turing-machine design depends on, and — per
Trey — "publishable on its own" if we can chart D vs model size.

## What happened

- **Overnight crash, diagnosed and fixed.** The first run crashed at width-32's final eval:
  `IndexOutOfRangeException` in `CharTokenizer.Decode` — the trained model argmaxed the reserved **pad id**
  during free generation and Decode indexed past its char array. Latent from the start; only a
  well-trained model triggers it. Fixed by skipping out-of-vocab ids in Decode, and wrapping each width in
  a try/catch that logs to file and continues (the crash had gone to stderr, invisible in the log).
- **Metric change, forced by the data.** We first defined D as "largest move-count with per-step accuracy
  ≥ 90%." It proved **too brittle**: D flipped 12 → 8 → 4 across widths whose accuracy curves were nearly
  identical — a single threshold-crossing point knife-edging near-equal models. Replaced with **mean
  per-step accuracy across all eval move-counts** (area-under-curve), which uses the whole curve. Both are
  logged; meanAcc is now primary. (Recomputed from the already-logged `DATA,` rows — no retraining.)
- **Trimmed epochs 4000 → 2000** after confirming meanAcc plateaus by ~epoch 500–1000.

## The finding: width saturates

| EmbedDim | params | mean per-step accuracy |
|----------|--------|------------------------|
| 32  | 26 K  | 66.0% |
| 64  | 101 K | 73.2% |
| 128 | 399 K | 73.1% |
| 256 | 1.6 M | 70.1% |

Across a **60× parameter range**, mean accuracy rises **once** (32→64, ~+7 points) then is flat-to-slightly
-down. **Width does not buy head-tracking distance past ~100 K params.** This is the strong form of
*mechanism-bound, not capacity-bound*: the head-tracking limit is set by the architecture (a NoPE model
reconstructing position through attention), and width cannot move it. The "you'd need exponential model
growth" quip from a few days ago, in miniature and measured.

Honest caveats (documented in [FINDINGS.md](../../examples/CoreTrainer.Examples.HeadTrack/FINDINGS.md)):
width 256 trained only 2000 epochs vs 4000 for 64/128, so its 70.1% may be mild undertraining rather than
real degradation — do not claim "width hurts." Single seed per width; treat 64–256 as "flat," not a rank
order. 512 skipped (plateau established at 16× params).

## Why this makes the next axis the real question

Width saturating doesn't mean the architecture is capped — it means width was the wrong dial. Head-tracking
is a *sequential accumulation*; **depth** adds compositional steps per forward pass where width only adds
precision the task stops needing. The next campaign (depth: Layers 1/2/4/6/8, width pinned) tests whether
head-tracking scales with depth where it didn't with width. If so, the headline becomes "context scales
with depth, not width." After depth: NoPE vs RoPE, the axis tied to the original question.

## Discipline notes worth keeping

- **The metric was the trap, not the model.** A brittle summary statistic (D@threshold) manufactured a
  fake non-monotonic result (w64=12 > w128=8) on curves that were actually equal. Whole-curve metrics
  first; sanity-check any scalar against the curve it summarizes.
- **Unattended runs must log their own crashes.** The first crash was invisible because it went to stderr;
  fixed with per-width try/catch into the file sink.
